# Codex / Gemini レビューワークフロー

実装フェーズ完了後に **必ず** 通すレビュー手順。

CLAUDE.md / AGENTS.md の方針: Claude Code が実装し、Codex / Gemini に第二意見を求める。

---

## いつ呼ぶか（タイミング）

実装の節目ごとに毎回呼ぶ:

| タイミング | 例 |
| --- | --- |
| ✅ フェーズ完了 | フェーズ A/B/C のような大きな単位の完了直後 |
| ✅ 仕様変更後 | `docs/race_type_policy.md` の方針変更を実装した直後 |
| ✅ 新規モジュール追加後 | `app/output_validation.py` のような新規ファイル作成後 |
| ✅ 大規模リファクタ後 | スコアリング・パイプライン構造の変更後 |
| ❌ 軽微な修正 | typo / 文言調整 / テスト1-2件追加のみ |
| ❌ ユーザーが「次へ」と指示 | 明示的に省略を許可されたとき |

理想は **コミット前** に呼ぶ。コミット後でも、push 前なら反映余地あり。

## 何を渡すか（情報の整理）

### 必須項目

1. **変更ファイル一覧** (`git diff --stat HEAD~1`)
2. **変更内容の要約** (3〜5 行)
3. **確認してほしい観点** (バグ / 設計 / テスト網羅性 / 命名 / セキュリティ 等)

### 推奨項目

4. **関連仕様参照** (`docs/race_type_policy.md` の該当セクション等)
5. **代替案** (検討したが採用しなかったアプローチ)
6. **テスト観点** (網羅すべき項目)
7. **判断に迷っているポイント**

### テンプレート

```markdown

- 実装フェーズ: <例: 広島9R 修正 (要件 1〜5)>

- <3-5 行>

### 変更ファイル
$ git diff --stat HEAD~1

### 確認してほしい点
- <観点1>
- <観点2>

### 代替案
- <あれば>

### テスト観点
- <網羅すべき項目>
```

## どう呼ぶか（CLI 実行手順）

### Codex

```bash
# 差分とレビュー観点を渡す
git diff HEAD~1 > /tmp/diff.txt
cat /tmp/diff.txt | codex review --context "docs/race_type_policy.md フェーズC home_area 拡張の差分。観点: 設計妥当性 / 命名 / テスト網羅性"
```

または対話モード:

```bash
codex
# プロンプトを貼り付けて対話
```

### Gemini

```bash
gemini "下記の差分をレビューしてください。docs/race_type_policy.md の仕様に従っているか確認。

$(git diff HEAD~1)
"
```

## どう反映するか（指摘の処理）

| 指摘の種類 | 対応 |
| --- | --- |
| **妥当 + 明確** | 追加コミットで対応。コミットメッセージに「codex/gemini レビュー反映」と明記 |
| **妥当だが大きな変更** | ユーザーに「こういう指摘があった、対応する？」と確認 |
| **的外れ / プロジェクト方針と異なる** | ユーザーに報告。「こういう指摘があったが、本プロジェクトは X 方針なので採用しない」 |
| **判断に迷う** | ユーザーに提示して判断を仰ぐ |

### NG: 黙って指摘を採用しない / 黙って却下しない

レビュー結果は必ずユーザーに **要約レポート** で伝える:

- 良い指摘 N 件 (採用 / 検討 / 却下)
- 的外れ N 件
- 判断保留 N 件
